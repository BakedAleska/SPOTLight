# Decisions

Single source of truth. Each entry is the decision plus why, in one or two lines, updated in place.

## Made
- **Phase (2026-10-10):** building. The system as built is mapped in `docs/ARCHITECTURE.md`; unused research was pruned on 2026-10-10 (still in git history).
- **Idea (2026-10-09):** an operator dashboard for NextEra's SPOT challenge (live replay + post-mission review). It's the only prompt with an internship prize, and sponsor tracks reward literal, on-prompt answers (winners-knighthacks-history).
- **Sponsor targets:** NextEra (core), Hugging Face, AMD, Neon, Figma, plus the auto-entered general tracks. Every sponsor's tech must be load-bearing, not a logo (synthesis §5: "sponsormaxxing").
- **Stack:** Next.js web app + FastAPI backend + Postgres/pgvector (Neon via the `neon` profile) + open HF models on the AMD box (Laya for System 1, Qwen3-Embedding for RAG, Qwen3.5-9B via llama.cpp for System 2), with a LiteLLM gateway and a LangGraph orchestrator. The user chose it; it maps one sponsor to each layer.
- **Two-tier AI:** System 1 = Laya plus the `policy.py` rules validator on every event (`TRIAGE_MODE` serial or parallel, rules-only if Laya is down); System 2 = an HF open-source model on AMD ROCm that explains escalated flags. This puts hard gates first and the LLM second (lablab "LLM proposes, gates decide"), and gives a measurable routing saving for AMD judges.
- **Repo layout (2026-10-10):** one repo (`SpotTheDOT`). AMD-side code lives in `amd/` with its own Python deps and runs on the Radeon Cloud box; the app talks to it only over HTTP. Judges review one public repo, and API-contract changes land in one commit.
- **Databricks dropped (2026-10-10).** We stick to AMD servers: Laya, fine-tuned on AMD, serves failure forecasts online (`/api/v1/system1/forecast`), and the backend computes the insights live in SQL. That's one fewer platform, and all model work stays on AMD.
- **System 2 context = custom read-only MCP server doing RAG on pgvector in Neon (2026-10-10).** Tools embed a query with an open-source embedding model hosted on AMD and retrieve from Neon pgvector with metadata filters; numeric stats stay plain SQL. Embedding model: **Qwen3-Embedding-0.6B** (1024-d, Apache-2.0; fallback snowflake-arctic-embed-l-v2.0), exact vector search at our scale (`research/tech-embedding-model-amd-2026-10-10.md`).
- **Logs + raw data in Neon (2026-10-10):** same database, schemas `raw` (SPOT data verbatim, append-only) and `app` (model calls, MCP tool calls, requests, jobs); `LOGS_DATABASE_URL` can split them out later. One connection string, and logs join to flags.
- **Containerize everything (2026-10-10):** every service ships a Dockerfile and joins a root docker-compose.yml, so the whole stack starts with one command; on the no-root AMD Jupyter VMs the same code runs in a venv.
- **Backend = FastAPI (2026-10-10)** in `backend/`, its own container: same language as Laya, the validator and the MCP client. Route tree in `docs/backend-services-contract.md`.
- **Laya runs in its own container (2026-10-10)** (`amd/system1/service/`, port 8082), called by the backend over HTTP; keeps the GPU/model concerns out of the API.
- **Keep LoRA for the Laya fine-tune (2026-10-10).** PEFT ports to other HF models. The gap vs full FT (run2 0.805 vs 0.733 real, 0.846 vs 0.602 counterfactual) most likely comes from setup (to be confirmed by the sweep): 3 epochs, LLRD on adapters, frozen norms, no training counterfactuals. Fixed in code and swept via `scripts/sweep_lora.sh`; compare on held-out F1/calib CE, never train loss.
- **Graph RAG in Neon (2026-10-10):** a knowledge graph as plain `kg_nodes`/`kg_edges` tables + pgvector on nodes + `WITH RECURSIVE` traversal (Neon has no Apache AGE/Cypher). Links the Spot manual, notes and incidents to assets, waypoints and failure types; contract §7 in `docs/system2-rag-contract.md`.
- **System 2 output mirrors Orbit's AI-inspection format** (question / answer / reasoning, plus a recommended action). NextEra operators already use Orbit (kit screenshots).

- **System 2 plan (2026-10-10):** prompt + grammar-JSON + deterministic post-check first; LoRA is a gated stretch, shipped only if it beats the prompt baseline. Fine-tuning teaches format, not facts (research R5).
- **System 2 model = Qwen3.8-27B only (2026-10-10, user decision; replaces the provisional Qwen3.5-9B).** Served as Unsloth GGUF `Qwen3.8-27B-Q8_0` + `mmproj-F16` via llama.cpp on the SSH W7900D (48 GB VRAM, gfx1100), with no fine-tune: newest Apache-2.0 Qwen at a size that fits one card, same `qwen3_5` architecture as the 9B so prompts and llama.cpp carry over. The 9B results stay as the historical baseline; Phase 4 numbers must be re-run on the 27B.
- **Keep Q8_0 and accept its measured latency (2026-10-10, user decision).** The Phase 4 held-out run (`amd/system2/results/report/amd-qwen38-27b-q8`) measured p50 11.2 s / p95 15.0 s (15003 ms, 2 of 40 attempts timed out) at ~22.5 tok/s, so p95 misses the 15 s budget by 3 ms; we keep 8-bit quality instead of the Q4_K_M fallback. The report stays as measured, unedited.
- **Cited namespaced IDs in claim text are references, not claims (2026-10-10).** The checker already allowed a bare cited ID (`V1`) in text, but split `action:A0030`/`flag:14` into an identifier/number and rejected supported claims; it now masks only exact, whole cited IDs (`grounding._mask_cited`). Uncited IDs and every number are still checked; the Phase 4 baseline rebuilds identical.
- **System 2 owns the flag contract (2026-10-10):** typed Pydantic contract, with flags faked from `policy.py` until Laya output is wired in, so System 2 isn't blocked on System 1.
- **System 2 adapts to the backend stack (2026-10-10, after 8aaac30):** the backend owns retrieval and POSTs one prepared MCP `get_flag_context` packet to System 2 on port 8083; the model does not call tools (tool loops break the ≤15 s p95). System 2 accepts the backend's request shape (unknown fields ignored, consumed fields validated, strict output), MCP action codes and doc_id citations, and drops its own CSV packet builder in favour of saved MCP packets.
- **System 2 eval leakage rule (2026-10-10):** headline numbers only on controlled held-out packets with nothing after the event's time, no target labels and no previously generated explanations; action quality is scored against human labels, with agreement against the validator's `suggested_action` reported separately.
- **AMD serving works on ROCm (2026-10-10):** Qwen3.5-9B Q4_K_M via a llama.cpp HIP build for gfx1151 ran fully on the GPU, 3/3 schema-valid replies, 35.6 tok/s generation, 12.4 s for 439 output tokens. Vulkan stays a fallback only.
- **System 2 eval (2026-10-10):** headline numbers on real mission-held-out flags only, with bootstrap CIs and a human-checked judge; the templated explanation is both the fallback and the baseline. Only ~40 real anomalies, so synthetic data can't inflate the numbers.
- **Model gateway = LiteLLM proxy on :4000 (2026-10-10; the user's "LightLLM", read as LiteLLM).** One OpenAI-compatible endpoint and key for every model (`system1`, `system2`, `system2-vision`, `embed`), pinned `litellm[proxy]==1.104.1` with a hashed lock; no retries, no fallback model, so a failure reaches System 2's checked template instead of a silent model swap.
- **Orchestrator = LangGraph service on :8085 (2026-10-10).** `/v1/assess` is a fixed graph (MCP context -> Laya -> route -> vision -> System 2 -> template) within one 40 s deadline and stays tool-free, so "System 2 does not call tools on /explain" still holds; only the new `/v1/ask` chat path has a bounded read-only MCP tool loop (<= 4 calls, 30 s). The backend uses it only when `ORCHESTRATOR_URL` is set, keeping its own path as the fallback.
- **Vision = separate CPU service on :8084 (2026-10-10): code computes every number.** OCR + code readers (thermal, gauge, spectrogram, Orbit screenshots) produce `V#` readings and an annotated image, with no model call; VLMs score 25-30 % on gauges/thermal, and code is deterministic and testable (research tech-spot-vision-cv §3, §7).
- **System 2 multimodal contract `2026-10-10.backend.2` (2026-10-10):** optional `context.vision` (citable `V#` rows, trust HIGH/LOW, LOW rows lose their value), `context.ocr` (untrusted, never citable) and `image_b64` (context only); a HIGH-trust tool/log disagreement removes MONITOR/NO_ACTION, and a server without `--mmproj` falls back to text-only. Additive: a `backend.1` request is unchanged.

- **Demo images never judge the asset (2026-10-10).** With `DEMO_IMAGES=1` the kit sample is illustrative: no logged value is sent to vision, demo rows carry no comparison, System 2 ignores agrees/delta on them, and the fine-tune learns disagreement only from `linked` rows. A kit image of another pump must not escalate this one.
- **Vision service fails closed (2026-10-10).** `VISION_API_KEY` required (compose dev default), JPEG/PNG/WebP only, 12 MP, body cap, 2 concurrent analyses: a 107 KB PNG of 25 MP had pushed one request to ~2.5 GB RSS.
- **Image requests get a longer deadline (2026-10-10):** System 2 25 s (`SYSTEM2_IMAGE_DEADLINE_S`, text stays 15 s), orchestrator System 2 node 28 s: image prefill needs room beyond 15 s (audit A-6), and the chain still ends inside the backend's 45 s.

- **Deployment (2026-10-10):** the frontend, the backend and the MCP server run on Vercel. The database is Neon. The GPU models run on the AMD box: Qwen3.8-27B (llama-server), Laya and the embedding model. Embeddings stay on AMD because Vercel Hobby functions get 2 GB of RAM and 1 vCPU, too small for Qwen3-Embedding-0.6B on PyTorch.
- **AMD box = supervised native processes, no Kubernetes (2026-10-11, user decision).** The pod can't run k3s (no CAP_SYS_ADMIN, seccomp filtered, read-only cgroups, no /dev/kmsg; `docs/AMD-K8S-PLAN.md` §3 gate fails), so llm, embed and Laya run under supervisord, loopback only. Its sshd refuses TCP and socket forwarding, so the laptop reaches them by running a stdio bridge over one multiplexed SSH connection (user-approved).
- **System 2 reports whether its model answers (2026-10-11, user decision).** Live `/health` adds `model_status` from a background 1-token probe every 30 s (never blocks /health; skipped while an assessment runs), and the backend marks `system2` `degraded` when it is `down`: before, a dead llama-server still showed `up`, and every explanation silently became the template. Setup and tunnel scripts: `deploy/amd-native/`.
