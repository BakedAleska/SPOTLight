# AMD run: Qwen3.8-27B on the SSH W7900D (System 2 serving + Phase 3/4 measurements)

**Scope (2026-10-10, user decision):** System 2 serves **Qwen3.8-27B only**, with no fine-tune, on the SSH
instance in [`docs/AMD-GPU.md`](AMD-GPU.md): Radeon Pro W7900D, gfx1100, 48 GB VRAM, root, no Docker,
**huggingface.co blocked** (use hf-mirror or rsync), `/tmp` only 4 GB. This replaces the earlier four-GPU bake-off
plan.

**Rules:**
- Only numbers produced by these commands go in the repo.
- Nothing in an `amd-*` results directory is edited by hand.
- The box is ephemeral: copy results off as soon as a step finishes.

## 0. Laptop: SSH config and tunnel
Add a `Host spot-amd` entry as in `docs/AMD-GPU.md` ("Access"), using the console's current IP and port.

## 2. Box: build llama.cpp for gfx1100 (once, ~10–15 min; run it in tmux)
```bash
which hipconfig hipcc cmake || pip install -q cmake ninja
cd /root && [ -d llama.cpp ] || git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp && HIPCXX="$(hipconfig -l)/clang" HIP_PATH="$(hipconfig -R)" \
  cmake -S . -B build -G Ninja -DGGML_HIP=ON -DGPU_TARGETS=gfx1100 -DCMAKE_BUILD_TYPE=Release && cmake --build build -j 16
ls -l build/bin/llama-server
```
**Unverified here:** ROCm comes as pip packages in `/opt/venv` (there's no `/opt/rocm`). If `hipconfig` is missing or
CMake can't find HIP, stop and paste the error. Don't switch to a different model or backend without asking.

- The hashes come from huggingface.co's API for revision `4ca7207…` (29.05 GB and 0.93 GB). hf-mirror is a
  third party, so both lines must print `OK`.
- If the mirror is slow, download on the laptop and run `rsync -aP <dir>/ spot-amd:/root/models/q38-27b/`.
- **Why Q8_0:** 29 GB + 0.9 GB + KV cache fits the 48 GB card, and 8-bit is near-lossless. If generation is too slow
  for the 15 s budget (step 5), the fallback is `Qwen3.8-27B-UD-Q4_K_M.gguf` (16.46 GB, sha256
  `322e194ff79741c7baa497c240f677f54b201b0efab44ca8e50f122b39123482`). Same model, smaller quant.

## 4. Box: serve it (in tmux, so it outlives SSH)
```bash
tmux new -d -s llama '/root/llama.cpp/build/bin/llama-server -m /root/models/q38-27b/Qwen3.8-27B-Q8_0.gguf \
  --mmproj /root/models/q38-27b/mmproj-F16.gguf --image-max-tokens 1024 -ngl all -fa on -c 16384 -np 1 -rea off \
  --host 127.0.0.1 --port 8080 --metrics 2>&1 | tee /root/llama-server.log'
until curl -s 127.0.0.1:8080/health | grep -q ok; do sleep 3; done; echo READY
curl -s 127.0.0.1:8080/v1/chat/completions -H 'Content-Type: application/json' -d '{"messages":[{"role":"user","content":"Reply with the word ok."}],"max_tokens":8,"chat_template_kwargs":{"enable_thinking":false}}' | python3 -m json.tool | grep -E '"content"|predicted_per_second'
```
- `-rea off` and `enable_thinking:false` matter: Qwen3.8 thinks by default, which would burn the 350-token budget.
- If startup rejects a flag (an older or newer build), drop that flag and note which one.
- If image answers look corrupted, retry with `-fa off` (llama.cpp #29629).

## Run log: 2026-10-10 on the W7900D (Q8_0 kept)
**Setup notes that differ from steps 1–4:**
- The pip ROCm in `/opt/venv` (10.0.0) has no HIP CMake package (`hip-lang-config.cmake`). Fix: install
  `rocm-sdk-devel` 10.0.0rc4 with `--no-deps` (from `rocm.prereleases.amd.com/whl-multi-arch/`; the box's proxy
  blocks AMD's servers, so download on the laptop and `scp` it), then run `rocm-sdk init` and build with
  `HIP_PATH="$(rocm-sdk path --root)"`. The devel tree's libraries are hard links to the installed 10.0.0
  runtime, so only the headers come from rc4.
- Export `LD_LIBRARY_PATH=$(rocm-sdk path --root)/lib` and `no_proxy=127.0.0.1,localhost`; otherwise
  `llama-server` can't find `libhipblas.so.3`, and `curl 127.0.0.1` goes through the egress proxy.
- `hf download` needs `HF_HUB_DISABLE_XET=1`; otherwise it bypasses the mirror for Xet storage and gets a 401.
- No `tmux` in the image: run `apt-get install tmux` with `-o Acquire::http::Proxy=$HTTP_PROXY`.

**Results:**
- Step 4: 21.2 tok/s generation and 30.0 GB of VRAM in use.
- Step 5: headline-eligible report in `amd/system2/results/report/amd-qwen38-27b-q8` (rebuild: identical);
  p50/p95 11188/15003 ms. The 3 ms p95 miss was accepted, so Q8_0 is kept (`research/decisions.md`).

**Multimodal smoke (step 6) failed first, then passed after a checker fix:**
- **What the image shows:** nothing. `gauge_disagree.json` carries a 1x1 PNG, so "image used" only proves the
  server accepted the image. The gauge facts come from the text row `V1` (tool 121.0 psi vs logged 114.2 psi).
  Reading a real gauge image is still unverified.
- **First answer:** cites `[V1, reading:R0053]`, `[action:A0030]`, `[flag:14]`, all supported by the rows, but
  writes the IDs into the claim text. The checker split `action:A0030` into the identifier `A0030` and
  `flag:14` into the number `14`, neither of which appears in the cited content, so it rejected the answer
  (`ungrounded_identifier`, `ungrounded_number`).
- **Cause:** the validator, not the model. `V#` evidence passes like any cited row (the fixture's reference
  reply has 0 errors), and a bare cited ID was already allowed in text; namespaced IDs weren't recognised.
- **Why the retry drops the image:** by design (audit A-6). Attempt 1 uses about 13 s of the 25 s budget, so
  attempt 2 has under `TEXT_RESERVE_S` (8 s) + `MIN_IMAGE_CALL_S` (4 s) left and goes text-only; over HTTP it
  then ran out of time and the template answered.
- **Fix:** `grounding._mask_cited` masks exact, whole cited IDs before scanning, with tests. After the fix:
  `x-system2-image: used`, `path llm`, cited `[V1, reading:R0053]`, cache miss then hit, and the Phase 4
  baseline still rebuilds identical.
